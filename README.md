# РКС-НР — адаптивная вёрстка

Статическая HTML/CSS/JS-реализация главной страницы по макету Figma. Контрольные размеры: 1920, 768 и 375 px.

## Локальный запуск

```bash
python3 tools/serve.py
```

После запуска открыть `http://localhost:4173/`.

Нужен именно `tools/serve.py`, а не `python3 -m http.server`: обычный сервер
не поддерживает HTTP Range, и перемотка видео ломается.

ничего не значил, поэтому теперь это `services/hero.webp`.

закрыт `.gitignore`. **При выкладке сайта его нужно залить на сервер
отдельно** — git его не принесёт. Копия, вместе с архивами исходников до
пережатия, лежит рядом с проектом в `Figma-adaptive-heavy-files/`.

## Замеры плавности

`tools/frame-check.py` считает просевшие кадры при прокрутке настоящим
колесом, `tools/cpu-profile.py` показывает, кто ест процессор,
`tools/work-trace.py` — сколько работы делает движок (растеризация,
отрисовка, пересчёт стилей).

Работа видеокарты меряется отдельно: `tools/gpu-trace.py` печатает время и
количество задач GPU и компоновщика, `tools/trace-diff.py` — разницу трейсов
двух вариантов по именам событий, `tools/scroll-probe.py` раскладывает кадры
по участкам прокрутки и показывает рядом вызовы GL и чтения раскладки. Они
понадобились, когда выяснилось, что счётчик кадров главного потока не видит
цену полноэкранного WebGL-слоя вовсе, — см. «Слой дизера: во что он
обходится».

**Счётчик кадров меряет и загрузку машины тоже.** На занятом MacBook один и
тот же код давал то 0, то 147 просадок, и просадки размазывались по
участкам, где их не было. Прежде чем верить цифрам, посмотрите `uptime`:
при load average около 3 замер повторяем до кадра, при 15 и выше — мусор.
Разбирать варианты правки на нагруженной машине можно по `work-trace.py`:
время в нём тоже шумит, а количество задач — нет.

Порядок сравнения вариантов — прогоны вплотную и в обоих порядках, иначе
разница в загрузке машины между прогонами выдаст себя за разницу в коде.

## Ресурсы и производительность главной

Главная — эталонная страница проекта: остальные приводятся к её решениям.

### Шрифты

`assets/fonts/*.woff2` — подрезанные до латиницы, кириллицы и пунктуации
версии. Исходные OTF/TTF (`LT Superior/`, `Roboto-Variable.ttf`) остаются в
репозитории как мастер-файлы, но страницами не подключаются: в них были
греческий, иврит, арабское письмо, деванагари и тайский — вместе около
мегабайта, который не отрисуется никогда. Итог: 968 КБ → 164 КБ.

Начертание Semibold (600) удалено из `styles.css`: его не запрашивало ни одно
правило, браузер его и не скачивал. Ось начертания Roboto подрезана до
диапазона 400-500 — единственных значений в вёрстке.

Вес шрифтов влияет на скорость напрямую: лоадер главной ждёт
`document.fonts.ready`, то есть до конца их загрузки страница физически не
показывается.

Пересобрать после правки шрифта — `fontTools` + `brotli`:

```bash
python3 tools/check-fonts.py   # все ли символы страниц покрыты
```

Скрипт проверяет каждый символ всех HTML и JS против cmap подрезанных файлов.
Два пропуска заведомо известны и были в исходниках: `№` в LT Superior и `→` в
Roboto — их и раньше подставлял системный шрифт.

### Изображения

- `width`/`height` есть у каждой фотографии: браузер резервирует место до
  загрузки, вертикальных сдвигов (CLS) не возникает.
- `loading="lazy"` у всего, кроме hero. Hero дополнительно в `preload` с
  `fetchpriority="high"` — это LCP-элемент первого экрана.
- Формат один — WebP. Три фотографии статистики приезжали в JPEG/PNG
  (712 КБ втроём, из них 252 КБ на PNG размером 380x350) и переведены в WebP:
  99 КБ. Исходники этих трёх — 500x334 против 2048 у остальных, то есть в
  блоке они масштабируются вверх; при возможности стоит взять кадры покрупнее.
- Дизер строит текстуру от размера блока на экране (`textureMaxEdge`,
  `textureOversample` в `SITE_DITHER_CONFIG`), поэтому исходники крупнее
  ~1600 px дают вес без выигрыша в картинке.

### Видео

`<video>` на главной размечено с `preload="none"`: файл весит десятки
мегабайт и лежит пятой секцией, обращаться к нему на первом экране незачем.
`video-player.js` поднимает `preload` до `metadata` через IntersectionObserver
за экран до секции — длительность и полоса прогресса появляются заранее, а
стартовая загрузка страницы к файлу не обращается вообще.

Разметка главнее: если шаблон явно задал `preload="metadata"` или `auto`,
плеер не вмешивается.

### Сетка: min-height и поток вместо координат

Десктопная раскладка главной была пиксельным переносом Figma: каждый блок
стоял на своей координате в `vw`, у секций была жёсткая `height`. Пока тексты
не менялись, это работало; из админки Bitrix любой абзац на строку длиннее
вылезал бы за границу секции или наехал на соседний блок.

Что сделано на главной:

- **`height` → `min-height`** у всех секций и карточек. Кадр макета остаётся
  минимумом, но блок растёт за содержимым.
- **`company-intro`, `stats`, `services`, `footer` — CSS Grid.** Колонки
  повторяют колонки макета, а вертикальные расстояния заданы отступами между
  элементами, а не координатой каждого абзаца.
- **`stats` разведена на две независимые колонки** (`.stats__aside` слева,
  `.stats__list` справа). Обёртка левой колонки на мобильном и планшете
  объявлена `display: contents` — там раскладка прежняя.
- **`services`: рельса залипающего интро больше не дублирует высоту списка.**
  Раньше `.services__intro-sticky { height: 77.6042vw }` было посчитано
  вручную как «5 карточек × 14.2708vw + 4 промежутка». Теперь высоту строки
  задаёт сам список, рельса тянется до неё, и шестая карточка из инфоблока
  продлевает залипание сама.
- **`footer`: три колонки макета** вместо трёх абсолютных координат; у колонок
  с бордюром `min-height`, поэтому лишний пункт меню больше не вылезает за
  линию.
- **`.project-card h3`** больше не `white-space: nowrap`.

**Ловушка, на которую стоит смотреть при переводе остальных страниц:**
`min-height` из базового правила НЕ перебивается более поздним `height`.
Если базовый блок получил `min-height`, то на каждом брейкпоинте, где высота
переопределяется, тоже нужен `min-height` (или явный сброс `min-height: 0`).
Иначе секция молча становится выше на разницу — так уехали `about.html` и
карточки услуг на планшете, пока это не поправили.

Секция `company-intro` в потоке на обеих страницах, где она есть. Привязка к
`body[data-site-page="home"]` снята: правила общие, а различается только
`row-gap` под лидом — на главной лид занимает 4 строки, на `about.html` 5,
а в исходном макете текст под ним начинался на одной и той же отметке
24.3229vw. Отсюда 5.25vw против 1.875vw. Поменяется длина лида — эти числа
трогать не нужно, зазор держится сам.

### Планшет и мобильный: поток ниже 1200 px

Десктоп перевели на поток раньше, диапазоны до 1200 px донесли отдельно.
Порядок был прежний: снять `baseline`, править одну секцию, сверять `run` на
1920, 1440, 1199, 820, 768, 600, 599, 500, 375.

- **Подвал.** Мобильный — колонка флекса, планшетный — та же сетка колонок,
  что на десктопе. Навигация начиналась на `4.1667vw`, контакты — на
  `calc(50% + 10px)`, поэтому третий трек сетки задан как
  `calc(50% + 10px - 48.6967vw)`: колонки стоят ровно там, где стояли
  абсолютом. Свободную высоту (когда `min-height` больше содержимого)
  забирает `margin-bottom: auto` у контактов — копирайт остаётся прижат
  к низу, а при росте содержимого отступ схлопывается сам.
- **Подвал `documents.html`.** Там были две фиктивные высоты: 362 px при
  содержимом 291 и 293 px при содержимом 206, а копирайт стоял внутри
  пустого хвоста контактов. Убраны. Логотип в этом подвале растёт по своим
  пропорциям (`height: auto`), поэтому в потоке подвал следует за ним: на
  500 px он выше на 24 px, на 599 — на 44; на 375 совпадает попиксельно.
  Раньше на 599 меню подъезжало к логотипу на 8 px.
- **Карточка новости на мобильном.** Блок с датой и заголовком стоял
  абсолютом на 225 px — ровно под картинкой (15 паддинга + 210 картинки),
  так что в потоке встаёт туда же. Ширину карточки ему возвращают
  отрицательные поля; высота 180 вместо 195, потому что прежние 195 доходили
  до нижнего края карточки, минуя её нижний паддинг.
- **Призыв на «Услугах», планшет.** Дескриптор стоял на `top: 405px;
  left: 44.0104%` поверх первой строки заголовка. Наложением он и остался —
  в одну колонку эти два блока не выстроить, — но держит его сетка секции.
  Боковые отступы пришлось убрать из `padding` в крайние треки: проценты в
  `grid-template-columns` считаются от контентной коробки, а координата
  считалась от всей ширины секции.
- **`company-intro`.** Текст стоял на 352 px (мобильный) и 318 px (планшет),
  а высота лида над ним гуляет от семи строк на 600 px до трёх на 1199 —
  на 600 текст упирался в лид вплотную, на 1199 висел в пустоте. Теперь под
  лидом постоянный зазор, как на десктопе: 58 px и 70 px. В эти числа входят
  2–3 px, которые SplitText забирает отрицательным нижним полем последней
  строки, — без поправки зазор отсчитывался бы от видимого низа текста.
  Ширины, под которые нарисован макет (375 и 768), совпадают попиксельно;
  на 500–599 и 820–1199 текст поднялся к лиду на 33–92 px.

Что осталось абсолютным сознательно: декоративная «лестница» в
`company-intro`, дескриптор и заголовок hero поверх кадра, кнопка на карте
контактов, стрелки карточек. Это наложения, в колонку они не выстраиваются.

### Страница «О компании»

`about-clients` («Нам доверяют») переведена из координат в поток. На десктопе
это сетка из двух колонок — слева заголовок с лидом (`about-clients__intro`),
справа сетка логотипов; граница колонок совпадает с декоративной линией
`::before`. На планшете и мобильном — одна колонка, вертикаль набирается
отступами секции и `margin-top`, а не `top`. Отступы сверху и снизу переехали
с `about-clients__logos` на саму секцию.

Заголовку нужен `width: max-content`: раньше ширину ужимал `position:
absolute`, в потоке блок занял бы всю колонку. Он длиннее своей колонки и
заходит в пустую первую ячейку сетки логотипов — так было и раньше.

Фиксированные высоты на странице остались там, где они осмысленны:
`about-hero` и `about-career__image` — кадрирующие полосы с
`object-fit: cover` (внутренняя картинка тянется по `height: 100%`, и
`min-height` её сломает), `.button` — ховер с двумя слоями текста под
`overflow: hidden`.

Лид `company-intro__lead` анимируется построчно (`lineUp`), как такой же блок
на главной. До этого он стоял на посимвольном `title` и был единственным
источником дёрганья на всём сайте: 17 просевших кадров из 1450 против нуля на
остальных девяти страницах. Подробности — в «Что держит кадр во время
скролла»; менять пресет обратно нельзя.

#### Проверка раскладки

`tools/layout-check.py` — попиксельная сверка текущего дерева со снимком «до».
Два локальных сервера отдают проект и его копию, headless-Chrome открывает на
каждом `tools/layout-probe.html`, тот грузит страницу в iframe нужной ширины,
снимает у всех классованных элементов `offsetLeft/Top/Width/Height`,
`getBoundingClientRect`, `offsetParent`, `display` и `position`, и печатает
JSON. Скрипт сравнивает два снимка с допуском 1 px.

    python3 tools/layout-check.py baseline                 # снимок «до», один раз
    python3 tools/layout-check.py run --page about.html    # сверка после правки
    python3 tools/layout-check.py shot --page about.html --scroll .about-clients --out /tmp/shots

`shot` снимает те же два кадра картинками — ими проверяется то, чего не видно
в координатах: порядок отрисовки, обрезка, декоративные линии.

#### Проверка текста на живучесть

`tools/text-stress.py` отвечает на вопрос «что сломается, когда текст правят
из админки». Каждый текстовый блок страницы по очереди становится на треть
длиннее и вдвое короче, и замеряется, что от этого произошло: строка вышла за
свою колонку, блок обрезан родителем, наехал на соседа, декоративная линия не
отступила перед выросшим текстом или не подтянулась за укоротившимся.

    python3 tools/text-stress.py                          # все страницы, все ширины
    python3 tools/text-stress.py --page index.html --width 1440
    python3 tools/text-stress.py --only hero__ --width 1920   # разбор одного блока

Тонкости, без которых прогон врёт:

- **Никакого `--virtual-time-budget`.** С ним Chrome перестаёт рисовать кадры,
  а вместе с ними молчат `requestAnimationFrame` и `ResizeObserver` — то есть
  всё, чем линии подстраиваются под текст. Проверка тогда показывает, что
  линия «не подтянулась», хотя в живом браузере она подтягивается. Поэтому
  прогон идёт в реальном времени, а результат страница отдаёт POST'ом на
  `/stress-result` (в `pre#probe` он тоже пишется — можно открыть руками).
- **`SplitText` с `autoSplit` возвращает исходный текст.** Он держит исходную
  разметку и пересобирает её при изменении размера, так что подменённый текст
  живёт до следующего кадра. Перед замером `split`/`revert` глушатся.
- **Стартовые состояния анимаций снимаются, а не игнорируются.** До своего
  ScrollTrigger блок стоит `visibility: hidden`, а линии — в `scaleY(0)`.
  Пробник перебивает правило видимости и снимает inline-стили, которые
  выставил GSAP; то, что задано в CSS, остаётся.
- **Порог видимости — 0.4px, а не 1px.** Линии в макете ровно в пиксель
  шириной, и на «> 1» они бы не попали в проверку.
- **Слова берутся из `innerText`.** В заголовках соседние `span` стоят без
  пробела, и `textContent` склеил бы их в несуществующее длинное слово.

Чего проверка не видит: линии, нарисованные псевдоэлементом (`::before`
секции «Нам доверяют»), — в дереве их нет, и такие места приходится сверять
руками по переменным, которые ставит скрипт страницы. В режиме `--only`
пробник печатает inline-стиль ближайшего предка с `--`-переменными: по нему
видно, поехали ли они за текстом.

Тонкости, на которых харнесс уже спотыкался:

- **Основной критерий — `offset*`, а не рект.** `hero__line` и карточки услуг
  анимируются трансформом, и `getBoundingClientRect` ловит их посреди твина.
- **Chrome с `--dump-dom` и `--screenshot` не всегда завершается сам.** Скрипт
  не ждёт выхода, а опрашивает файл и потом убивает процесс.
- **Кадр может сняться до применения CSS и шрифтов.** `--virtual-time-budget`
  убегает вперёд реальной сети, и под нагрузкой страница успевает измериться
  неоформленной. Пробник проверяет, что все `link[rel=stylesheet]` отдали
  `cssRules` и что `document.fonts.check` знает оба семейства; прогон с
  `ready: false` повторяется. Без этой проверки сверка тихо врала —
  «до» приходило без стилей, и расхождением выглядела вся страница.
- **Обёртки SplitText из замера исключены**: они пересобираются на каждом
  ресайзе. Классы состояния (`is-`, `has-`, `gsap-`) в ключ элемента не идут.
- **Ширина `video-slider__buffer` зависит от буферизации** — в игноре.
- **Дизер иногда не успевает нарисовать картинку ниже первого экрана.** В
  headless под нагрузкой кадр снимается с пустым блоком, и попиксельное
  сравнение показывает разницу в четверть кадра. Проверяется повтором: если
  со второго раза расхождение исчезло — это гонка отрисовки. Геометрический
  прогон (`run`) от этого не страдает, он не смотрит на пиксели.
- **Скриншот не видит трансформы, а `run` не видит их намеренно.** Параллакс
  карточек преимуществ сместился, и поймал это только `shot`. Если правка
  меняет геометрию элемента, на который навешан ScrollTrigger, — проверять
  картинкой обязательно.

- **На планшете лид первого экрана обрезался.** `services-hero__title` имел

  уходил под обрез: на 600 px пропадало полторы строки. После `min-height`
  секция выросла на 130 px (600 px), 70 px (700 px) и 10 px (768–820 px).

- **`gap: 15px` из базового правила протекал в десктопную сетку.** Карточки
  разъехались на 15 px по колонкам и рядам. В десктопном правиле нужен явный
  `gap: 0`.
- **Карточки растягивались на высоту ряда.** Ряд выше карточки на величину
  разбега соседей, а `align-items` у сетки по умолчанию `stretch`. Нужен
  `align-items: start`.
- **Параллакс карточек считался от `.advantages__grid`.** Пока сетка была
  `position: absolute; inset: 0`, её рект совпадал с секцией. В потоке сетка
  занимает не всю секцию, и диапазон ScrollTrigger сократился с 1658 до
  1109 px — карточки поехали на 15 px в другом месте экрана. Триггер переведён
  на `.advantages` в `animations.js`.
- **Секция «преимущества» стала на 1 px выше.** Высота теперь складывается из
  отступов, заголовка и сетки, и каждое слагаемое округляется отдельно.
  Карточки при этом сместились на 0.03–0.06 px — в попиксельном сравнении
  видно только по сглаживанию волосяных рамок.

- браузер по такой ссылке никуда не прокручивает — прокрутку к вкладкам

  равен нужному (пришли по `policies.html#ethics` и жмём тот же пункт в
  подвале), события смены хеша не будет и страница не отреагирует.

Номера разделов пустые (`<span class="document-section__number" aria-hidden>`)
— в отличие от документов, политики не нумерованы, но пустой span сохраняет
ту же колонку под заголовком. Строка «Политика ООО «РКС-НР» по охране труда»

### Служебное: 404, карта сайта, robots

- **`404.html`** — обложка и подвал те же, что у документов, своё только тело
  сообщения (`not-found.css`). Помечена `noindex, follow` и в карту сайта не

  /404.html` в Apache, `error_page 404 /404.html;` в nginx); в Bitrix за это
  отвечает `404.php` шаблона.
- **`sitemap.xml`** — все десять страниц сайта. Инструменты разработки

  динамические адреса и карта станет генерируемой модулем «Поисковая
  оптимизация» — тогда статический файл удалить, чтобы не было двух
  источников.
- **`robots.txt`** — кроме инструментов разработки закрыты архивы исходников
  `assets/images/_original/` и `assets/images/about/raw/`. На боевой сервер
  их лучше вообще не выкладывать: на сайте они не используются, вместе это
  около 50 МБ.
- При переносе на боевой домен origin меняется в трёх местах: `canonical` и
  `og:url` каждой страницы, `loc` в карте и строка `Sitemap:` в `robots.txt`.

### Что держит кадр во время скролла

Правки, которые стоит сохранять при доработке остальных страниц:

- **Чтения и записи не чередуются.** `initProjectLineGaps` в `script.js`
  сначала снимает все `getBoundingClientRect`, потом пишет все CSS-переменные.
  Иначе запись кастомного свойства инвалидирует стиль и следующее чтение
  форсирует полный пересчёт раскладки — на каждом кадре скролла.
- **Атрибуты пишутся только на переходе.** `syncDesktopMenu` вызывается
  на каждом кадре скролла, но `tabIndex`/`aria-hidden` трогает, только когда
  значение действительно меняется.
- **`will-change` не постоянный.** Слой поднимается на время наведения
  (стрелки новостей и проектов) или пока секция идёт по экрану (карточки
  услуг, бегущая строка) и отпускается обратно. Постоянный `will-change`
  держит композиторный слой всю жизнь страницы.
- **Никакого `closest()` в рендер-цикле.** `services-dither.js` кэширует
  признаки элемента при измерении, а скрытость (`[hidden]`, фильтр проектов)
  пересчитывает по MutationObserver.
- **`matchMedia` — один объект на функцию**, а не новый MediaQueryList на
  каждый вызов.
- **Дизер не работает вхолостую.** `render` в `services-dither.js` сначала
  считает, попадает ли хоть одно фото в кадр (чистая арифметика по
  сохранённой геометрии, без единого вызова GL), и на пустом кадре гасит
  canvas через `hidden`, а не очищает его. Без этой проверки слой очищался и
  композитился 60 раз в секунду даже на секциях, где фотографий на экране
  нет: `IntersectionObserver` держит `item.visible` с запасом в 100 px,
  поэтому цикл продолжал крутиться. Замер на главной, scrollY 1200:
  было `clear=60, draw=0` в секунду при полноэкранном буфере 2520×1178 —
  стало `0/0`. Это давало просадку ровно там, где рисовать нечего, и было
  главной причиной жалоб на «лаги при скролле» на главной и «О компании» —
  двух страницах, где фотографий с дизером больше всего.
  Проверять после правок дизера: на позиции без фото в кадре `clear`
  должен быть нулевым, а на позиции с фото — прежним.
- **Посимвольная анимация — только для коротких заголовков.** Пресет
  `title` разбивает текст на символы и анимирует каждый отдельным элементом.
  На заголовке в три слова это ничего не стоит, на абзаце — это сотни узлов,
  которым браузер каждый кадр пересчитывает стиль и заново растеризует текст.
  Лид «О компании» (189 символов) стоял на `title` и давал 17 просевших
  кадров из 1450 при том, что все остальные страницы сайта дают ноль; тот же
  блок на главной с самого начала стоял на `lineUp`. Для длинного текста
  берём `lineUp` — он анимирует строки (здесь их 5 вместо 189 символов).
  Порог по замерам: посимвольно 4393 задачи растеризации, по словам ~2000,
  построчно 1615.
- **`.image-tone::after` больше нет.** Слой ничего не рисовал: правило
  `background: none !important; opacity: 1 !important` гасило его до конца, но
  пустой абсолютный слой оставался на каждом фото сайта. Убран вместе с
  правилами, которые им управляли, — ховерами карточек проектов, новостей и
  галереи новости и тремя правилами видео. Все они перебивались тем же
  `!important`, так что вид не изменился: `getComputedStyle` на всех девяти
  страницах давал у 44 блоков `.image-tone` фон `rgba(0, 0, 0, 0)` без
  градиента, блендинга, тени и рамки. Общий тон по-прежнему держит
  `.image-tone::before`.

### Слой дизера: во что он обходится

Владелец сказал, что прокрутка подлагивает, и что проверкой на удаление нашёл
виновника — фотографии. Разбор 9 сентября 2026 подтвердил жалобу и уточнил
её: платим не за сами картинки, а за общий WebGL-слой, который их рисует.

Инструменты, сделанные под этот разбор:

    python3 tools/gpu-trace.py http://localhost:4173/index.html --label база
    python3 tools/scroll-probe.py http://localhost:4173/index.html
    python3 tools/trace-diff.py http://localhost:4173/index.html --idle

`gpu-trace.py` снимает трейс с категориями `gpu`, `viz`, `cc` и печатает
время и количество задач видеокарты. Он нужен потому, что `frame-check.py`
считает просевшие кадры главного потока, а полноэкранный слой стоит не там:
в headless счётчик кадров показывает 0.3 % и проблему не воспроизводит вовсе.
`scroll-probe.py` раскладывает кадры по участкам прокрутки и рядом показывает
вызовы `drawArrays`, `clear` и `getBoundingClientRect`. `trace-diff.py`
прогоняет два варианта подряд и печатает разницу по именам событий.

Замеры на машине владельца, окно 1680×928 при DPR 2 — как в живом браузере;
главная, 14 с прокрутки колесом.

    вариант                                задачи GPU   время GPU
    база                                         4892     2068 мс
    без services-dither.js                        882     1072 мс
    без .webp — фотографий нет вовсе               817     1027 мс
    слой считает и рисует, но display: none       831     1074 мс

Первые две строки совпадают: **сами изображения не стоят ничего, вся разница
— дизер**. Четвёртая строка совпадает с ними же: слой, который по-прежнему
считает геометрию, гоняет шейдер и заливает текстуры, но не попадает к
компоновщику, обходится ровно как его отсутствие. Значит платим не за шейдер
и не за JS, а за то, что canvas каждый кадр отдаётся компоновщику.

Проверено по отдельности, разницы нет ни у одного:

- заглушен `drawArrays` — 4929 задач против 4892 у базы;
- заглушен `clear` — 4870;
- `premultipliedAlpha: true`, `alpha: false`, `desynchronized: true`,
  `powerPreference: 'low-power'` — все в пределах разброса.

**Разброс между прогонами одного и того же варианта: 3312, 4446, 4892
задачи.** Отсюда правило: сравнивать только прогонами вплотную и в обоих
порядках, а разницу меньше чем в полтора раза не считать разницей. Первый
подход к этим же атрибутам дал «выигрыш 20 %», который при чередовании
прогонов исчез — машина за полчаса просто разгрузилась.

Что именно добавляет слой (`trace-diff.py`, 10 с прокрутки, разница со слоем
и без): `TextureLayer::PushPropertiesTo` 977 штук — по одному на кадр,
`CommandBuffer::Flush` +1860, `IOSurfaceImageBacking::WaitForCommandsToBeScheduled`
+977, `WebGL` 1733 события на 600 мс, `RunTask` +15667 на 1572 мс. Это цена
одной синхронизации полноэкранной IOSurface с компоновщиком на каждом кадре.

**Слой работает и когда страница стоит.** Тот же замер без прокрутки, стоя на
секции с фотографиями: +14216 задач за 10 с, `Graphics.Pipeline` 750 мс
против 204 мс. Ничего не движется, а браузер шестьдесят раз в секунду
пересобирает кадр. Причина в шейдере: `drift` и `pulse` считаются от `uTime`,
то есть узор дышит всегда, а `bayer4(gl_FragCoord.xy)` привязан к пикселям
экрана, а не к картинке — поэтому и при прокрутке содержимое слоя меняется
целиком.

**Уменьшать слой почти бесполезно.** Объединяющий прямоугольник видимых фото
занимает по главной 3–45 % экрана (изредка до 88 %), в среднем около 20 %, —
казалось бы, есть что резать. Но canvas на 20 % площади дал 1393 мс против
1669 мс у базы при трёх прогонах вперемешку, то есть около 17 %, да и те
частично от того, что при мелком canvas фотографии чаще выпадают из его рамки
и слой гасится целиком. Цена — сама синхронизация на кадр, а не число
пикселей. Идея «рисовать дизер только в области видимых блоков», записанная в
HANDOFF как нетронутая, этими замерами закрыта: она не окупается.

Что из этого следует. Полностью убрать цену нельзя, не трогая вид: слой
обязан обновляться каждый кадр, пока узор анимирован и привязан к экрану.
Зато в покое шестьдесят обновлений в секунду не нужны никому — это и
сделано, см. ниже.

### Дизер в покое обновляется реже

`render` в `services-dither.js` собирает подпись кадра: длины и координаты
всех рисуемых прямоугольников, поворот, прозрачность, `ditherAmount`,
`ditherTarget`, энергия курсора, размер холста. Это арифметика по уже
посчитанной геометрии, без единого чтения раскладки. Совпала с подписью
прошлого нарисованного кадра — на экране ничего не изменилось, и слой
обновляется не чаще `IDLE_FPS` (по умолчанию 18). Любое движение — прокрутка,
курсор, проявление по наведению, кроссфейд, параллакс — меняет подпись и
возвращает полную частоту в том же кадре.

Половинная частота **при прокрутке** проверялась раньше и отклонена
владельцем: эффект отставал от вёрстки. Здесь отставать не от чего, а `drift`
и `pulse` считаются от времени медленно.

Частота в покое зашита константой `IDLE_FPS` в `services-dither.js`; на время
разбора она выносилась в адрес как `?idlefps`.

Замеры, два круга вперемешку, `tools/gpu-trace.py`:

    покой, 10 с            слой в компоновщик   команды WebGL   задачи GPU
    прежнее поведение              601 / 601      1015 / 1016    1082 / 1092
    18 к/с в покое                 157 / 172        270 /  291     367 /  341

    прокрутка, 3 с         слой в компоновщик   команды WebGL   задачи GPU
    прежнее поведение              276 / 290        443 /  467    1478 / 1822
    18 к/с в покое                 293 / 297        470 /  479    1836 / 1946

Прокрутка не изменилась вовсе, холостой ход упал в три с половиной раза.
Узор при этом продолжает дышать: два снимка в покое с интервалом 0.6 с
различаются на 3.6 % пикселей и в новом варианте, и в старом.

**Осторожно с длиной прогона.** Главная выше окна всего на 7261 px, а колесо
в инструментах идёт по 100 px каждые 50 мс — до низа страницы доезжает за
3.6 с. Прогон на 10 с — это на треть прокрутка и на две трети стояние внизу,
и на таком прогоне правка «частота в покое» ошибочно выглядит как выигрыш при
прокрутке. Мерить прокрутку с `--seconds 3`.

Остались непроверенными:

- **`powerPreference: 'high-performance'`** у контекста WebGL. На этом
  MacBook две видеокарты (Intel HD 530 и Radeon Pro 450), и атрибут держит
  включённой дискретную. Выигрыша в замерах он не даёт, а машину греет.
- Слой стоит примерно удвоения работы видеокарты на кадр прокрутки, и это
  остаётся.

Побочная находка. На секции проектов каждый кадр прокрутки читается
раскладка: `initProjectLineGaps` в `script.js` снимает десять
`getBoundingClientRect` (по три на карточку плюс секция) и пишет CSS-переменные,
и так по кругу. Чтения и записи там уже разделены, но само чтение живой
геометрии на каждом кадре остаётся — `scroll-probe.py` показывает 4–4.9
вызова на кадр на участке 2000–4000 px, при нуле на остальной странице.
В общем времени это мало (`Layout` — 116 мс за 14 с), поэтому трогать не
стали, но если владелец будет и дальше показывать на секцию проектов,
разбирать надо отсюда: `--project-line-height` действительно меняется каждый
кадр, а `--projects-line-N-x` — нет, и его можно писать только на изменение.

### Второй заход: сколько слой стоит именно при прокрутке

Владелец сказал «получше, но баги остались». Первый разбор завышал цену
слоя, и вот почему: главная доезжает до низа за 3.6 с, а прогоны шли по
10–14 с. Две трети замера страница просто стояла внизу, то есть в цифры
попадал холостой ход, который к тому моменту уже был вылечен.

Чистая прокрутка, 3 с колесом, два круга вперемешку:

    вариант                     задачи GPU        время GPU
    слой работает              1903 / 1931      957 / 926 мс
    слой погашен                628 /  632      709 / 727 мс

То есть при настоящей прокрутке слой добавляет около четверти работы
видеокарты, а не удваивает её. Растеризация при этом одинаковая (3023 против
3033 задач) — своё рисование страницы слой не трогает.

Главный поток при прокрутке простаивает: `tools/cpu-profile.py` даёт 93.2 %
`(idle)`, из JS наверху сам `render` дизера с 48 мс за 25 с. Искать в
скриптах нечего.

Что проверено и отвергнуто в этом заходе:

- **Гашение слоя между секциями не даёт всплеска.** Гипотеза была, что
  возвращение canvas из `hidden` заставляет компоновщик заново заводить слой
  ровно в момент въезда секции с фото. Замер по 4 возвращениям за проход:
  худший кадр рядом с ними 16.8 мс, как и везде.
- **Разрешение слоя почти ни при чём.** Буфер в девять раз меньше по
  пикселям (dpr 0.5 вместо 1.5) экономит 12 % времени GPU: 832/843 мс против
  944/953.
- **`premultipliedAlpha: true`** — 889/888 мс против 896/929. В пределах
  разброса.
- **`powerPreference`** — разницы в headless нет ни в какую сторону.

Что даёт эффект: **площадь экрана, которую слой закрывает.** Холст полосой в
30 % высоты окна — 799/797 мс против 909/959 у полноэкранного при 709/727 у
погашенного, то есть возвращается больше половины цены слоя. Часть этого —
от того, что при узкой полосе фотографии чаще выпадают за её край и слой
гасится целиком, но не вся.

### Выключатели для сравнения вживую (убраны после разбора)

Замеры в headless на этой задаче упёрлись в потолок: разница между вариантами
меньше разброса, а просевших кадров headless не показывает вовсе. Судил
владелец, а для этого в адрес выносились режимы `?idlefps`, `?ditherscroll`,
`?ditherband`, `?gpu`, `?nodither` и `?lerp`, каждый с плашкой режима в левом
нижнем углу.

**Разбор закончен, выключатели и плашка из кода убраны** — как и после
прошлого разбора дизера. В коде остались только те правки, которые владелец
подтвердил; что именно, написано ниже в «Итоге». Понадобятся снова —
восстанавливать тем же приёмом и обязательно с плашкой: без неё владелец
путал вкладки и отвечал про не ту страницу.

### Половинная частота при прокрутке со сдвигом слоя (проверено, не оставлено)

Половинную частоту при прокрутке владелец однажды уже отверг: эффект
обновлялся через кадр и отставал от вёрстки. Режим `?ditherscroll=30` снимал
именно это возражение — на пропущенном кадре слой не перерисовывается, а
сдвигается трансформом ровно на то, на сколько уехала страница. Фотографии
остаются на своих местах, а компоновщику сдвиг готового слоя обходится
дешевле нового кадра.

Замер, 3 с прокрутки, два круга: команды WebGL 205/199 против 479/477,
задачи GPU 987/966 против 1322/1315. Времени GPU это заметно не меняет.

Две тонкости, на которые пришлось наступить:

- **Сдвиг округляется до целого пикселя экрана.** Дробный сдвиг заставляет
  компоновщик пересемплировать слой, а узор дизера — сетка в один пиксель.
- **Холст делается выше окна на 160 px сверху и снизу**, иначе сдвинутый слой
  открывает непрокрашенную полосу у края. Из-за этого «центр экрана» для
  внутреннего параллакса и сетка узора считаются теперь от окна, а не от
  холста: `viewportHeight` и `uGridOffset`. При холсте по размеру окна оба
  равны прежним значениям, и штатный вид не меняется — сверено с версией из
  git, расхождение 0.061 % при собственном разбросе дизера 0.02–0.06 %.

**Остаточное расхождение у самого режима — 22 % пикселей, и это не ошибка
раскладки.** Холст с запасом имеет другой размер, а буфер дизера всегда в
1.5 раза крупнее CSS при экране в 2 раза — то есть слой в любом случае
пересемплируется при выводе. Другой размер холста даёт другую дробную часть
этого пересемплирования, и часть точек узора переворачивается. Структура,
размер точки и плотность те же: попиксельно 22 %, на глаз два снимка
неразличимы, а при холсте по размеру окна тот же режим даёт 0.18 %.
Проверено бисекцией: увеличение холста в любую сторону, само по себе и без
всякого дросселирования, даёт те же 21–24 %.

Отсюда правило: **любое изменение размера холста дизера сдвигает узор.**
Сверять такие правки попиксельно бесполезно — сравнивать надо структуру, а
решать должен владелец глазами.

### Слой полосой: сделано, проверено, выигрыша нет, из кода убрано

Владелец сравнил режимы и сказал, что `?nodither` лагает меньше всего. Значит
дело действительно в слое, и следующим кандидатом была полоса: рисовать
холст по видимым фотографиям, а не во весь экран. Режим включается
`?ditherband=on`.

Как сделано. После сборки кадра `updateBand` берёт объединяющий
прямоугольник видимых фотографий и подводит под него коробку холста. Высота
берётся из лестницы в четыре значения (30 %, 55 %, 80 % и полная высота
окна), а не подгоняется вплотную: **каждое изменение размера холста заново
пересемплирует узор**, и подгонка на каждом кадре давала бы мерцание сетки.
Положение округляется до целого пикселя экрана по той же причине. Отсечение
фотографий из кадра считается теперь от окна, а не от холста — иначе полоса
выкидывала бы из кадра те самые фотографии, под которые её надо подводить.

Проверено, что режим корректен:

- фотографии стоят на своих местах — при усреднении дизера расхождение с
  обычным режимом 0.93 из 255 при лучшем совпадении на нулевом сдвиге;
- полоса покрывает фотографии целиком: на секции проектов фото занимают
  335–732 px окна, полоса встаёт 318–750; на первом экране фото −400…385,
  полоса 0–432;
- вместе с `?ditherscroll` полоса честно вырождается в полный холст, потому
  что к ней добавляется запас под сдвиг с обеих сторон.

**Выигрыша по замерам нет.** Три круга вперемешку, 3 с прокрутки:

    вариант          задачи GPU (три круга)
    полный экран        1518 / 1926 / 1886
    полосой             1951 / 1675 / 1712
    слой погашен         793 /  676 /  665

Медианы 1886 против 1712, то есть около 9 % при разбросе в полтора раза.
Время GPU не различается вовсе.

Ранний грубый замер обещал больше половины: холст, прибитый CSS к полосе в
30 % высоты, давал 799 мс против 909. Это была **загрязнённая проверка**:
при фиксированной полосе фотографии часто выпадали за её край, слой гасился
целиком, и экономия шла оттуда, а не от площади. Правильная полоса, которая
всегда накрывает фотографии, так не экономит.

Вместе с замером разрешения (буфер в девять раз меньше по пикселям — 12 %)
это закрывает вопрос: **цена слоя держится на самом факте его обновления
каждый кадр, а не на числе пикселей.** Убрать её полностью можно только не
обновляя слой — то есть либо реже (`?ditherscroll`), либо никогда
(`?nodither`).

### Невидимые слои фотографий рисовались наравне с видимыми

Владелец сказал, что лаги начинаются с третьего блока и что все режимы дизера
ощущаются одинаково. Третий блок — статистика, и в нём нашлось вот что.

В разметке статистики четыре снимка лежат друг на друге
(`stats.webp`, `stats-1841`, `stats-405`, `stats-2275`), из них виден один, а
три ждут своей очереди в кроссфейде с `data-dither-opacity="0"`. Ровно так же
устроен блок новостей: ещё три слоя с нулевой прозрачностью. Дизер рисовал их
все: полный проход шейдера по площади фотографии ради результата, который
блендинг по `SRC_ALPHA` всё равно отбрасывает.

`render` теперь пропускает слой с `opacity <= 0.001`. Замер вызовов
`drawArrays` на кадр по участкам (`tools/scroll-probe.py`):

    участок прокрутки        было      стало
    статистика, 1200-2000    3.6-4.0   0.9-1.0
    новости, 6000-6800       4.0-4.2   1.2-1.8

Вид не изменился: попиксельно 0.006 % на статистике и 0.150 % на новостях
против версии из git при собственном разбросе дизера до 0.15 %. Кроссфейд
работает как раньше — как только прозрачность поднимается выше нуля, слой
снова попадает в кадр.

### Сравнение с референсом владельца

`oci.madebybuzzworthy.com` снят теми же инструментами, 3 с прокрутки, окно
1680×928 при DPR 2:

    показатель            референс     наша
    задачи GPU                2233     1791
    время GPU              2274 мс  1456 мс
    отрисовка (Paint)          462     2142
    растеризация              3665     3003
    узлов в DOM                762      517

**Референс делает больше работы на видеокарте, чем мы.** У него тоже
полноэкранный WebGL-слой, причём в полном разрешении экрана (3360×1570
против нашего 2520×1178), и тоже Lenis. Значит дело не в объёме работы.

Два отличия, которые видно:

- **Его холст лежит под содержимым (`z-index: -1`), наш — поверх
  (`z-index: 2`).** Проверить это замером не удалось: слой под непрозрачными
  фонами секций компоновщик просто выбрасывает из сцены, и цифры получаются
  не про порядок слоёв, а про то, что слоя фактически нет. У нас так не
  выйдет: фон секций закрыл бы фотографии.
- **Мы рисуем в 4.6 раза чаще: 2142 события отрисовки против 462.** Каждое
  дешёвое (0.057 мс), но их около двенадцати на кадр — это анимации текста,
  бегущая строка и CSS-переменные линий проектов.

### Инерция прокрутки: у нас вдвое медленнее, чем у референса

`initSmoothScroll` в `script.js` держит `lerp: 0.052`. Референс, с которого
брали образец, работает на голом Lenis со стандартным `lerp: 0.1`; в
комментарии к коду записано, что значение снижали «по ощущениям» — сперва на
четверть, потом ещё на треть.

Чем меньше lerp, тем дольше страница ползёт после жеста и тем мельче её шаг
на кадр. На таком медленном равномерном ползании любой сбой кадра виден
гораздо сильнее, чем на быстром коротком движении: глаз ведёт постоянную
скорость и спотыкается о разрыв. При этом просевших кадров в замере может
не быть вовсе.

Владелец сравнил 0.052, 0.075 и 0.1 и выбрал 0.1. **На этом значении он
перестал отличать страницу с дизером от страницы без него, хотя на 0.052
разница была очевидна.** Это и оказалось главной причиной жалоб: не объём
работы, а то, на каком движении эта работа видна.

`lerp: 0.1` теперь стоит в `initSmoothScroll`. `syncTouchLerp` оставлен
прежним (0.039): на мобильном жалоб не было, а трогать тач без проверки на
устройстве смысла нет.

У более быстрой инерции есть и измеримый побочный эффект — страница
успокаивается раньше, и дизер раньше уходит в экономный режим. За 6 с после
жеста, два круга:

    инерция    слой отдан компоновщику    команды WebGL
    0.052              111 / 112             186 / 193
    0.1                 90 /  90             154 / 151

Дополнительно: длинных задач JS во время прокрутки нет ни одной. Просадки
кадров начинаются со `scrollY` около 3000 и растут к низу страницы — это
ровно та часть, где дизер работает непрерывно (2-2.6 отрисовки на кадр
против 0.8 выше по странице).

### Итог разбора прокрутки

Что осталось в коде из всего перебранного:

1. **Дизер в покое обновляется 18 раз в секунду вместо 60.** Холостая работа
   упала в три с половиной раза, вид не изменился.
2. **Полностью прозрачные слои фотографий не рисуются.** В блоках статистики
   и новостей это вчетверо меньше отрисовок на кадр, вид не изменился.
3. **Инерция прокрутки 0.1 вместо 0.052.** Именно после этого владелец
   перестал видеть разницу с выключенным дизером.

Что проверено и НЕ оставлено: половинная частота при прокрутке со сдвигом
слоя, слой полосой по видимым фотографиям, снижение разрешения буфера,
`premultipliedAlpha`, выбор видеокарты, порядок слоя относительно
содержимого. Цифры по каждому — выше в этом разделе; повторять эти опыты
незачем.

Чего мы так и не сделали и что осталось известным отличием от референса: он
рисует в 4.6 раза реже нас (462 события отрисовки против 2142 за 3 с
прокрутки). Это анимации текста, бегущая строка и CSS-переменные линий
проектов. Если жалобы вернутся — копать надо здесь.

### Известные ограничения

- **Дескриптор hero переносится сам.** Раньше он лежал в разметке двумя
  копиями с разными местами `<br>`: SplitText учитывает `<br>` независимо от
  `display`, и переключить переносы одним CSS не выходило. Любая правка текста
  из админки ломала обе копии — слова свисали за колонку, строк становилось
  четыре вместо трёх. Теперь это один абзац без жёстких переносов: колонка на
  десктопе доведена до правого поля макета (22.6563vw при левом крае
  74.2188vw — ровно до 96.875vw), на мобильном ограничена 300px, чтобы текст
  ложился в три строки, а не в две во всю ширину, длинное слово рвётся по
  `overflow-wrap`. Обе вертикальные линии правой колонки на десктопе теперь
  считаются от фактических границ абзаца (`--hero-descriptor-top` /
  `--hero-descriptor-bottom`, их публикует `initTextBoxVars` в
  `script.js`) с одним и тем же отступом — как на планшете. Раньше их концы
  стояли на фиксированных долях высоты, и отступы разъезжались: на 1920×1080
  сверху 50px, снизу 74px. Предлоги держатся на своих строках через `&nbsp;` —
  это единственное, что стоит сохранить при правке текста в Bitrix.
- **Линии первого экрана считаются от текста.** Верхняя пара в правой колонке
  отбивается от дескриптора, нижние засечки — от заголовка, отступ у всех
  один (`--hero-description-line-gap`). Раньше концы стояли на долях высоты:
  до заголовка оставалось 18px на 1920×1080 и 37px на 1440×900, а заголовок
  в одну строку оставлял под собой дыру в 134px.
- **Заголовок «Нам доверяют» больше не `white-space: nowrap`.** Он стоит по
  своей длине, но не длиннее колонки до второй вертикальной линии, а разрыв
  в первой линии считается по фактическому боксу заголовка
  (`--clients-title-*`). Раньше разрыв стоял на
  фиксированных 5.7292–12.5vw, то есть был подогнан ровно под текущий текст
  в одну строку.
- **Название пятой услуги — один текст, а не две копии.** Перенос по слогам
  делает `hyphens: auto` при `lang="ru"`; вторая копия с ручным дефисом
  «Специализирован-ный» удалена вместе с правилами показа.
- **Заголовок «Наши преимущества» тоже переносится**, а три линии под ним и
  засечка над ним начинаются от его фактических границ
  (`--advantages-title-*`). Раньше это были доли ширины (8.3333vw сверху,
  15.1042vw снизу), подогнанные под заголовок ровно в одну строку.

  Общий приём один на все эти места: блок помечается `data-box-var="имя"`,
  `initTextBoxVars` в `script.js` публикует его коробку переменными
  `--имя-top` / `--имя-bottom` на его секции, а CSS подставляет их в
  координаты декора. Запасные значения в CSS — исходные координаты макета,
  так что без JS страница выглядит как раньше.
- **Пункты подвала без своей страницы** размечались `<span class="footer__nav-pending">`,
  а не `<a href="#">`: ссылка в никуда — тупик для краулера и скринридера.
  Все три (охрана труда, этика, противодействие коррупции) теперь ведут на
  `policies.html`, страниц без адреса не осталось, и класс вместе с его
  правилами удалён. Появится новая заглушка — тот же приём: `span`, а не
  `href="#"`.
- **Текст показателей в блоке статистики на десктопе идёт с `opacity: .4`** —
  это контраст 2.38:1 при минимуме 4.5:1. Значение подсвечивается по
  наведению и по фокусу (отсюда `tabindex="0"` у `.stat-item`), но в покое
  текст читается плохо. Порог проходит `opacity: .65` (4.8:1) — правка
  заметная, поэтому оставлена на решение дизайна.
- **Лоадер держит экран минимум 2 с** (`MIN_DISPLAY_MS` в `script.js`).
  Это осознанный приём, но LCP при этом гарантированно не меньше ~2.4 с.
- **На планшете три секции были ниже собственного содержимого** и оно
  вываливалось в следующий блок: `projects` на 91 px (кнопка «Все проекты»
  стояла вплотную к заголовку «Услуги»), `services` на 5 px (обрезалось
  через `overflow: hidden`), `news__header` на 15 px. После перехода на
  `min-height` секции содержат свой контент, и всё ниже опустилось на 134 px.
  Это исправление, а не смещение макета, но разница видимая — если нужен
  прежний плотный вид, уменьшать надо отступы, а не высоту секции.

## Видео и Bitrix

`video-player.js` независимо инициализирует все `[data-video-player]`. Источники
находятся в HTML (`video > source`), а не в JavaScript, поэтому шаблон CMS может
подставлять что угодно. После AJAX-вставки вызовите
`window.RKSVideoPlayer.init(container)` на родителе новых блоков; повторная
инициализация уже подключённого плеера безопасна. `window.RKSVideoPlayer.get(frame)`
отдаёт `{ video, play, pause, seek, destroy }`.

### Разметка

```html
<section class="video-section" aria-label="Видео о компании">
  <div class="video-frame" data-video-player>
    <!-- необязательная рамка-бегущая строка: 4 блока .video-frame__ticker -->
    <div class="video-frame__media image-tone image-tone--hero">
      <img src="cover.webp" alt="…">          <!-- обложка, её рисует дизер -->
    </div>
    <video class="video-frame__video" poster="cover.webp" preload="metadata"
           playsinline webkit-playsinline controls aria-label="Видео о компании">
      <source src="company.mp4" type="video/mp4">
    </video>
    <button class="play-button" type="button" aria-label="Воспроизвести видео">
      <img src="/assets/icons/play.svg" width="127" height="127" alt="">
    </button>
  </div>
</section>
```

При инициализации плеер создаёт `.video-frame__stage` — сестринский слой к
`.video-frame__media` — и переносит туда `<video>`, кнопку play и собранную
панель управления.

Так сделано намеренно: у `.image-tone` есть `isolation: isolate`, а общий
WebGL-дизер (`services-dither.js`) — это `position: fixed; z-index: 2` в корне
документа. Всё, что лежит внутри `.image-tone`, запирается в её stacking context
и уходит ПОД дизер; именно поэтому кнопка play раньше была не видна до старта
видео. Сцена с `z-index: 3` находится в корневом контексте и рисуется поверх
дизера, при этом обложка остаётся в `.image-tone` и дизер её обрабатывает как
прежде.

Следствие: `.video-frame__media` и `.video-frame__stage` обязаны иметь одинаковую
геометрию. В `styles.css` им задан общий `inset: var(--ticker-media-inset)`.
**Переопределяя геометрию на конкретной странице, меняйте оба селектора сразу**
(пример — `news-detail.css`). Если шаблон изменит только обложку, плеер заметит
расхождение через `ResizeObserver` и выровняет сцену сам, но правильный CSS
дешевле.

### Что умеет панель

Пуск/пауза, полоса с буфером и подсказкой времени, живая перемотка
перетаскиванием, громкость (раскрывается по наведению, запоминается в
`localStorage`), скорость 0,5–2×, субтитры при наличии `<track>`, мини-плеер
(Picture-in-Picture), полный экран, индикатор загрузки и сообщения об ошибках.
Панель прячется через 2,8 с бездействия во время воспроизведения.

Клавиши при фокусе области видео: `Space`/`K` — пауза, `←`/`→` — 5 секунд,
`J`/`L` — 10 секунд, `↑`/`↓` — громкость, `0`–`9` — переход к проценту ролика,
`Home`/`End` — начало/конец, `M` — звук, `F` — полный экран, `C` — субтитры,
`P` — мини-плеер. Ползунки — `role="slider"` со своей раскладкой стрелок,
`Home`/`End` и `PageUp`/`PageDown`. Двойной клик по кадру — полный экран.

Ползунки собраны из `div`, а не из `input[type="range"]`: нативный элемент
по-разному ведёт себя при перетаскивании в разных движках, а полосу буфера и
подсказку времени он не поддерживает вовсе.

Без JavaScript остаются нативные `controls` браузера. Громкость на телефоне
регулируется системными кнопками, шкала громкости там скрыта; кнопка отключения
звука остаётся в панели.

### Шаблон Bitrix

Готовый шаблон: `includes/video-player.php`. Он принимает массив `$siteVideo`,
экранирует все значения, пропускает только локальные абсолютные пути и `http(s)`
(никаких `javascript:`/`data:`), сам подставляет MIME по расширению и ничего не
выводит без источника.

```php
$siteVideo = [
    // одиночный файл…
    'src'     => CFile::GetPath($arResult['PROPERTIES']['VIDEO_FILE']['VALUE']),
    // …или несколько источников, браузер выберет первый поддерживаемый
    'sources' => [
        ['src' => '/upload/…/company.webm', 'type' => 'video/webm'],
        ['src' => '/upload/…/company.mp4',  'type' => 'video/mp4'],
    ],
    'poster'  => CFile::GetPath($arResult['PROPERTIES']['VIDEO_POSTER']['VALUE']),
    'title'   => $arResult['PROPERTIES']['VIDEO_TITLE']['VALUE'] ?: $arResult['NAME'],
    'alt'     => 'Строительство жилого комплекса',  // alt обложки, по умолчанию title
    'ticker'  => $arResult['PROPERTIES']['VIDEO_TICKER']['VALUE'],
    'tracks'  => [
        ['src' => '/upload/…/ru.vtt', 'srclang' => 'ru', 'label' => 'Русские', 'default' => true],
    ],
    'preload' => 'metadata',   // none | metadata | auto
    'loop'    => false,
    'muted'   => false,
    'section' => true,         // false — вставить только .video-frame, без <section>
];
include $_SERVER['DOCUMENT_ROOT'] . '/includes/video-player.php';
```

`$siteVideo` читается один раз на include. Для двух роликов на странице
переопределите массив перед каждым включением.

### Что сделать в Bitrix (в этом репозитории установки нет)

Front-end готов и переносится как есть. Оставшееся делается один раз на боевом
сайте.

**1. Свойства инфоблока.** Тип «Файл» для `VIDEO_FILE` (при необходимости
множественное — тогда `VALUE` придёт массивом ID) и `VIDEO_POSTER`, тип
«Строка» для `VIDEO_TITLE` и `VIDEO_TICKER`, «Файл» для `VIDEO_SUBTITLES`.
В настройках файлового свойства проверьте поле разрешённых расширений: если оно
заполнено, добавьте туда `mp4` (и `vtt` для субтитров) — иначе админ получит
отказ при загрузке.

**2. Файлы в шаблон.** `includes/video-player.php`, `styles.css`,
`video-player.js` и `assets/icons/play.svg`. Пути внутри шаблона (`play.svg`
задан как `/assets/icons/play.svg`) поправьте под каталог вашего шаблона.
`styles.css` и `video-player.js` подключаются один раз в `header.php`/`footer.php`,
а не рядом с каждым видео.

**3. Сборка `$siteVideo`.** В `result_modifier.php` шаблона компонента:

```php
<?php
// bitrix/templates/…/components/bitrix/news.detail/…/result_modifier.php
$video = [];

$fileId = $arResult['PROPERTIES']['VIDEO_FILE']['VALUE'] ?? null;
// Множественное свойство отдаёт массив ID — собираем все как <source>.
foreach ((array) $fileId as $id) {
    $path = CFile::GetPath($id);
    if ($path) {
        $video['sources'][] = ['src' => $path];   // MIME шаблон определит сам
    }
}

$posterId = $arResult['PROPERTIES']['VIDEO_POSTER']['VALUE'] ?? null;
if ($posterId) {
    $video['poster'] = CFile::GetPath($posterId);
}

foreach ((array) ($arResult['PROPERTIES']['VIDEO_SUBTITLES']['VALUE'] ?? []) as $id) {
    $path = CFile::GetPath($id);
    if ($path) {
        $video['tracks'][] = ['src' => $path, 'srclang' => 'ru', 'label' => 'Русские'];
    }
}

$video['title']  = $arResult['PROPERTIES']['VIDEO_TITLE']['VALUE'] ?: $arResult['NAME'];
$video['ticker'] = $arResult['PROPERTIES']['VIDEO_TICKER']['VALUE'] ?? '';

// Пустой массив источников — шаблон просто ничего не выведет.
$arResult['SITE_VIDEO'] = $video;
```

И в `template.php` компонента:

```php
<?php $siteVideo = $arResult['SITE_VIDEO']; ?>
<?php include $_SERVER['DOCUMENT_ROOT'] . '/includes/video-player.php'; ?>
```

**4. Лимиты загрузки — самое частое место отказа.** Ролик на 70 МБ не
загрузится с настройками PHP по умолчанию (`upload_max_filesize` обычно 2M,
`post_max_size` 8M): админка молча вернёт пустое поле. В `php.ini` нужно как
минимум:

```ini
upload_max_filesize = 256M
post_max_size = 256M
max_execution_time = 600
max_input_time = 600
memory_limit = 256M
```

После правки перезапустите php-fpm. Проверить применившиеся значения удобно
через «Настройки → Инструменты → Проверка системы» либо `phpinfo()`.

**5. Отдача файла.** `/upload/` должен отдаваться веб-сервером напрямую, с
поддержкой HTTP Range — см. следующий раздел. На стандартном Bitrix VM с nginx
это работает из коробки; ломается, если файл проксируется через PHP.

**6. Проверка.** После первой загрузки откройте страницу и убедитесь, что
консоль браузера чистая: предупреждение `[RKSVideoPlayer] Сервер отдаёт видео
без поддержки HTTP Range…` означает пункт 5. Синтаксис шаблона на боевом
сервере проверяется одной командой:

```bash
php -l /path/to/includes/video-player.php
```

### Требования к файлу и серверу

MP4 с H.264/AAC и faststart (атом `moov` в начале файла); плеер сохраняет
пропорции без обрезки. Сервер/CDN обязан отдавать файл с правильным
Content-Type и поддержкой HTTP Range: `Range: bytes=0-1023` → `206`,
`Content-Range` и 1024 байта
([MDN](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Audio_and_video_delivery/buffering_seeking_time_ranges)).

**Без Range перемотка физически невозможна.** Браузер это честно сообщает:
`video.seekable` вырождается в `[0, 0]` — «перемотать никуда не могу», хотя
`duration` при этом известна. Любая попытка задать `currentTime` в такой
ситуации отбрасывает ролик в начало: снаружи это выглядит как «видео
начинается сначала».

Проверить свой сервер одной командой — нужен ответ `206`, а не `200`:

```bash
curl -sI -H "Range: bytes=0-1023" https://ваш-сайт/upload/company.mp4 | head -3
```

Или открыть страницу и посмотреть консоль: плеер печатает предупреждение
`[RKSVideoPlayer] Сервер отдаёт видео без поддержки HTTP Range…` с полным
путём к файлу.

Что делает плеер, когда Range нет:

- не трогает `currentTime` — ролик не отматывается в начало;
- гасит ползунок и пишет причину прямо в кадре;
- предлагает кнопку «Загрузить ролик целиком»: файл скачивается одним
  запросом и играется из `blob:`-ссылки, где перемотка работает всегда.
  Только по явному нажатию — ролик может весить десятки мегабайт.

Настоящее лечение — на сервере: отдавайте файл статикой nginx/Apache/CDN из
`/upload/` и не проксируйте его через PHP без поддержки Range. Локальный
`tools/serve.py` диапазоны поддерживает; `python3 -m http.server`, VS Code
Live Server и большинство простых «live server» — нет.

Полный экран использует Fullscreen API; в top layer уходит `.video-frame__stage`,
то есть бегущая рамка туда не попадает. На iPhone предусмотрен нативный
`webkitEnterFullscreen` ([Apple](https://developer.apple.com/documentation/webkit/delivering-video-content-for-safari)).
Под видео 16:9 на экране другой пропорции остаются чёрные поля letterbox —
поэтому градиент панели в полноэкранном режиме доведён до непрозрачного
чёрного: иначе на стыке была видна «чёрная заливка под градиентом».

### Проверки плеера

При запущенном локальном сервере:

```bash
python3 tests/video-range.py
PLAYWRIGHT_PATH=/path/to/node_modules/playwright node tests/video-player.cjs
```

Браузерные проверки используют установленный Google Chrome: обе страницы, ширины
375/768/1440, слои (сцена выше дизера, кнопка play не перекрыта, панель совпадает
со сценой), воспроизведение и пауза, перемотка кликом/перетаскиванием/клавиатурой
на паузе и на ходу, скорость, звук, полный экран (без бегущей строки, во весь
экран, градиент до чёрного), автоскрытие панели, конец ролика и повтор, ошибка
загрузки, нативные controls без JS. Скриншоты сохраняются в `/tmp/player-*.png`.

`tests/player-harness.html` — отдельный стенд плеера без остальной страницы и без
дизера: удобно смотреть панель управления и отлаживать вёрстку.

Для Safari/iOS и Firefox нужен отдельный прогон в поддерживаемом окружении;
эмуляция ширины окна не заменяет проверку на физических устройствах.
